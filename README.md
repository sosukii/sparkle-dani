# Sparkle Dani

Интернет-магазин изделий ручной работы Мари: каталог с фильтрами, карточки товаров, корзина и связь с мастером через Telegram.
Онлайн-оплаты и админ-панели нет — так задумано на этом этапе.

**Стек:** Nuxt 4 · Vue 3 · TypeScript (strict) · Tailwind CSS 4 · Pinia · Vitest · Playwright.

> Каталог сейчас состоит из **демонстрационных товаров** (54 шт., `isDemo: true`) с нарисованными иллюстрациями и пометкой «демо-изображение».
> Тексты «Обо мне» и «Покупка и доставка» — тоже примеры. Всё это помечено на сайте и заменяется настоящими материалами Мари.

## Быстрый старт

```bash
nvm use                           # Node 22
npm ci
npx playwright install chromium   # браузер для e2e и визуальных тестов
npm run dev                       # http://localhost:3000
```

Production-проверка: `npm run build && node .output/server/index.mjs`.

### Git-хуки и CI

- `pre-commit` (Husky) запускает полный `npm test`, включая скриншоты. Упавшие проверки блокируют коммит. `--no-verify` без договорённости не используем.
- `pre-push` не повторяет работу: если дерево коммита уже прошло `pre-commit`, он это пропускает, иначе запускает `npm test`.
- GitHub Actions (`.github/workflows/ci.yml`) выполняет те же команды на push и pull request (Ubuntu, Node из `.nvmrc`). При падении сохраняет отчёт и скриншоты как артефакт `playwright-artifacts`.

### Визуальные тесты — как с ними работать

- 27 снимков: главная, каталог (обычный, с фильтрами, пустой, 2-я страница), товар (в наличии / под заказ), корзина (с товарами / пустая), диалог заказа, «Обо мне», «Доставка», 404, мобильная панель фильтров.
- Допуск намеренно жёсткий: `maxDiffPixels: 40`, `threshold: 0.01`. Широкий допуск скрывал реальные поломки: низкоконтрастный блок (бежевый на белом) проходил незамеченным.
- Анимации отключены, шрифты свои (не системные), данные демо-каталога фиксированы, ожидание — по состоянию (шрифты, ленивые картинки, сеть), а не `sleep`.
- Эталоны раздельные по платформам: `tests/visual/__screenshots__/darwin/…` (локально, macOS) и `…/linux/…` (CI).
- **Эталоны не обновляются автоматически.** Если тест упал: откройте `npx playwright show-report` или `test-results/*/…-diff.png`, разберитесь, поломка это или ожидаемое изменение. Только если ожидаемое — `npm run test:visual:update` и проверьте `git diff` по PNG.
- **Linux-эталоны** берутся из самого CI: после изменения вёрстки запушьте, дождитесь падения шага `test:visual`, скачайте `gh run download <id> -n playwright-artifacts` и положите нужные `*-actual.png` из `test-results/` под именем эталона в `tests/visual/__screenshots__/linux/pages.spec.ts/`. (Для новых снимков они уже лежат в `tests/visual/__screenshots__/linux/`.)

## Архитектура

```
app/                      # клиент (Nuxt 4: srcDir = app/)
  pages/                  # index, catalog/[category], product/[slug], cart, about, delivery
  components/             # AppImage, ProductCard, CatalogView, CatalogFilterPanel, OrderDialog …
  stores/cart.ts          # Pinia: корзина + localStorage
  composables/usePageSeo.ts
server/
  repositories/           # ← единственная точка доступа к данным
  api/                    # /api/products, /api/products/[slug], /api/products/by-ids, /api/categories, sitemap-источник
  plugins/compress-html.ts
shared/                   # код, общий для клиента и сервера (+ unit-тесты)
  types/                  # zod-схемы и типы
  utils/                  # catalog-query (фильтры/поиск/сортировка/фасеты), cart, format, seo, site (константы)
data/                     # JSON каталога (не в public/)
public/images/            # фото
tests/{unit,e2e,visual}
docs/DATA.md              # формат данных
```

### Как устроено хранение товаров и как перейти на БД

- `server/repositories/product.repository.ts` — интерфейс `ProductRepository` (`listProducts`, `getProductBySlug`, `getProductsByIds`, `listCategories`, `getTaxonomy`) и фабрика `getProductRepository()`.
- Сейчас фабрика возвращает `json-product.repository.ts`: читает `data/` через Nitro server assets (попадают в сборку), валидирует zod-схемами, битые файлы пропускает с понятным логом, кэширует в памяти (в dev перечитывает на каждый запрос).
- Логика фильтрации, поиска, сортировки, фасетов и пагинации **не зависит от хранилища**: она работает с массивом товаров (`shared/utils/catalog-query.ts`).
- Переход на SQLite/MongoDB: напишите `sqlite-product.repository.ts`, реализующий тот же интерфейс, верните его из `getProductRepository()`. API-обработчики, страницы и компоненты менять не нужно. Для очень больших каталогов фильтры можно перенести в запросы БД, оставив ту же форму ответа `CatalogResult`.
- Админ-панель в этот этап не входила. Прежде чем редактировать товары через интерфейс, нужно отдельно спроектировать авторизацию и постоянное хранилище; запись в JSON-файлы как в базу не используется.

### Корзина и Telegram

- Корзина — Pinia + `localStorage` (ключ `sparkle-dani:cart:v1`), читается после гидратации; битые данные отбрасываются. Синхронизация между вкладками. На странице корзины цены и остатки подтягиваются с сервера (`/api/products/by-ids`), исчезнувшие товары помечаются и не входят в сумму.
- Лимиты: для «в наличии» с заданным `stock` — не больше остатка; если остатка в данных нет — только технический потолок 99 шт. Ограничений не выдумываем.
- Кнопка «Связаться с Мари» открывает диалог с составом заказа и суммой. Текст **ничего не отправляет автоматически**: покупатель копирует его и сам открывает Telegram (`https://t.me/<TELEGRAM_USERNAME>`). Так состав заказа не уходит третьим лицам.
- Сейчас в `TELEGRAM_USERNAME` временно стоит `sosukii` — **замените на контакт Мари** в `shared/utils/site.ts`.

### Изображения

Компонент `AppImage` строит `<picture>` с AVIF → WebP → JPEG и явным `srcset` (240–1200 px), `width/height` против сдвигов вёрстки, качество 82 (на демо-иллюстрациях AVIF-превью весят 9–12 КБ без видимых артефактов). Главная картинка первого экрана — `priority`: без lazy, `fetchpriority=high`, `preload`. Остальные — `loading=lazy`. Ресайз на лету делает `@nuxt/image` (IPX + sharp), кэш в браузере 7 дней.

### SEO

Уникальные `title`/`description`, canonical, Open Graph (`usePageSeo`), `sitemap.xml` (страницы, категории, товары) и `robots.txt` (`/cart` закрыт) через `@nuxtjs/sitemap` и `@nuxtjs/robots`; фильтры, поиск и корзина — `noindex`; нормальные 404 со статусом 404; JSON-LD `WebSite` на главной и `Product` — только для не-демо товаров.

## Принятые решения

- **Nuxt 4, а не 3.** В ТЗ указан Nuxt 3, но на октябрь 2026 актуален Nuxt 4 (это тот же Vue/Nitro с обновлённой структурой `app/`), ветка 3.x устаревает. Вся архитектура прежняя.
- **Своя `AppImage` вместо `<NuxtPicture sizes="…">`.** Разбор `sizes` в `@nuxt/image` давал мусорные варианты (`1×1`, `2×2`) и ломал картинки; явный `srcset` предсказуем и тестируем.
- **Корзина читается через `onNuxtReady`, а не `app:mounted`.** `app:mounted` срабатывает до окончания гидратации страниц с асинхронными данными, из-за чего разметка расходилась с серверной.
- **Сжатие HTML — серверным плагином.** Не нужен отдельный прокси, но Nuxt собирает страницу ошибки внутренним подзапросом, поэтому он исключён (иначе бинарное тело ломалось). JSON из `/api/*` лучше сжимать на уровне прокси/CDN.
- **Теплота / сезон.** В ТЗ поле названо «Теплота / сезон» без деталей; сделан справочник «Тёплое / Демисезон / Лёгкое» (необязательное поле). Меняется в `data/taxonomy.json`.
- **Кнопка «Связаться с Мари».** В ТЗ имя «Даня», по решению заказчика на сайте — «Мари» (одно и то же лицо). Имя вынесено в константу `OWNER_NAME`.
- **Google Stitch не использовался:** в этом окружении он не подключён, дизайн сделан вручную.

## Известные ограничения и что дальше

- Демо-контент (товары, иллюстрации, тексты «Обо мне» и «Доставка») нужно заменить настоящим; контакт Telegram — на контакт Мари; сведения об оплате и доставке — заполнить.
- `sharp` собирается под архитектуру машины сборки (сейчас `darwin-arm64`): деплойте сборку на ту же платформу или собирайте на сервере/в CI под целевую (`npm ci && npm run build`).
- Эталоны скриншотов для macOS и Linux хранятся отдельно; обновление Linux-эталонов пока ручное через артефакт CI (см. выше). Можно автоматизировать отдельным workflow или Docker-образом Playwright.
- E2E и скриншоты против production-сборки занимают около минуты на коммит; параллелизм ограничен двумя воркерами, потому что картинки кодируются на лету и нагружают процессор.
- Нет: онлайн-оплаты, админ-панели, отзывов/рейтингов, многоязычности — по ТЗ.
