# Sparkle Dani

Интернет-магазин NOCTURNE: авторский вязаный трикотаж ручной работы Дани. Каталог с фильтрами, карточки товаров, корзина и связь с мастером через Telegram.
Онлайн-оплаты и админ-панели нет — так задумано на этом этапе.

**Стек:** Nuxt 4 · Vue 3 · TypeScript (strict) · Tailwind CSS 4 · Pinia · Vitest · Playwright.

> Каталог пока состоит из демонстрационных товаров (24 шт., `isDemo: true`) с временными картинками-заглушками (не фотографии изделий); настоящие изделия, фото и сведения Дани добавляются по инструкции в [`docs/DATA.md`](docs/DATA.md). Демо-набор покрывает все фильтры, категории и случаи «сведения не известны».

## Быстрый старт

```bash
nvm use                           # Node 22
npm ci
npx playwright install chromium   # браузер для e2e и визуальных тестов
npm run dev                       # http://localhost:3000
```

Production-проверка: `npm run build && node .output/server/index.mjs`.
Статическая сборка (как на GitHub Pages): `npm run generate` → `.output-static/public`.

### Git-хуки и CI

- `pre-commit` (Husky) запускает полный `npm test`, включая скриншоты. Упавшие проверки блокируют коммит. `--no-verify` без договорённости не используем.
- `pre-push` не повторяет работу: если дерево коммита уже прошло `pre-commit`, он это пропускает, иначе запускает `npm test`.
- GitHub Actions (`.github/workflows/ci.yml`) выполняет те же команды на push и pull request (Ubuntu, Node из `.nvmrc`), плюс `test:static`. При падении сохраняет отчёт и скриншоты как артефакт `playwright-artifacts`.
- Уведомление в Telegram после деплоя: задайте в GitHub (Settings → Secrets and variables → Actions) секреты `TELEGRAM_BOT_TOKEN` (токен бота от @BotFather) и `TELEGRAM_CHAT_ID` (id вашего чата с ботом; сначала напишите боту любое сообщение). После каждого успешного деплоя бот пришлёт ссылку. Без секретов шаг пропускается.
- Деплой (`.github/workflows/pages.yml`) запускается **только после успешного CI** на `main` и публикует статическую сборку на GitHub Pages. Можно запустить и вручную (Actions → Deploy to GitHub Pages → Run workflow).

### Визуальные тесты — как с ними работать

- 49 снимков (десктоп и мобильный): главная, каталог (обычный, с фильтрами, много фильтров в одну строку, пустой, с изделиями без сведений, 2-я страница), товар (в наличии / под заказ / с размерами / без сведений), справка по размеру, корзина (с товарами / пустая), диалог заказа, «О бренде», «Покупка и доставка», «Свой заказ», «Материалы и уход», «Размеры и мерки», поиск (разделы, синонимы, пустой), 404, мобильная панель фильтров.
- Допуск намеренно жёсткий: `maxDiffPixels: 40`, `threshold: 0.01`. Широкий допуск скрывал реальные поломки: низкоконтрастный блок (бежевый на белом) проходил незамеченным.
- Анимации отключены, шрифты свои (не системные), данные демо-каталога фиксированы, ожидание — по состоянию (шрифты, ленивые картинки, сеть), а не `sleep`.
- Эталоны раздельные по платформам: `tests/visual/__screenshots__/darwin/…` (локально, macOS) и `…/linux/…` (CI).
- **Эталоны не обновляются автоматически.** Если тест упал: откройте `npx playwright show-report` или `test-results/*/…-diff.png`, разберитесь, поломка это или ожидаемое изменение. Только если ожидаемое — `npm run test:visual:update` и проверьте `git diff` по PNG.
- **Linux-эталоны** берутся из самого CI: после изменения вёрстки запушьте, дождитесь падения шага `test:visual`, скачайте `gh run download <id> -n playwright-artifacts` и положите нужные `*-actual.png` из `test-results/` под именем эталона в `tests/visual/__screenshots__/linux/pages.spec.ts/`. (Для новых снимков они уже лежат в `tests/visual/__screenshots__/linux/`.)

### Один код для сервера и статики

Сайт работает и как Node-приложение (SSR), и как **полностью статический** (GitHub Pages, без сервера):

- Сервер отдаёт весь каталог одним `GET /api/catalog.json` (при статической сборке это обычный файл).
- Страницы берут данные через `loadCatalog()` + `useAsyncData`. При SSR/пререндере в HTML попадает только нужный срез (12 карточек, одна страница товара), а дальше фильтры, поиск, сортировка и пагинация считаются **в браузере** теми же функциями из `shared/utils/catalog-query.ts`, что и на сервере.
- Статический HTML собирается без query-параметров, поэтому на статике первый рендер каталога считается без них и настоящие параметры применяются сразу после гидратации (иначе клиент и HTML разошлись бы на ссылках вида `?page=2`).
- Для каждого товара и категории создаётся своя страница (`nitro.prerender` + хук в `nuxt.config.ts`), для неизвестных адресов — `404.html`.

### Поиск

Поиск **без ИИ и внешних сервисов**: он мгновенный, работает на статическом хостинге, не добавляет вес и не влияет на Web Vitals.
Для каталога из сотен товаров это доли миллисекунды в браузере.

- `shared/utils/search.ts` — нормализация, упрощённая русская основа слова (формы «розовая/розовый», «серьги/серьга»), словарь синонимов (`SYNONYM_GROUPS`: «сережки» = «серьги», «шапочка» = «шапка», цвета и сезоны) и разбор намерений в запросе: «в наличии», «под заказ», «до 2000», «от 2 тыс», «недорогие».
- `shared/utils/site-search.ts` — разделы сайта со словарём ключевых слов и готовым коротким ответом (`SITE_PAGES`): «как получить», «где магазин», «какой город», «где на карте» → «Покупка и доставка» (СДЭК или лично в Москве); «цены» → каталог; «размеры», «премиум», «бюджет» → «Свой заказ»; «написать», «телеграм» → Telegram.
- Страница `/search?q=…` показывает сначала подходящие разделы с ответом, потом изделия; она помечена `noindex`.
- Поиск в каталоге использует тот же движок, плюс фильтр «Наличие».
- **Как улучшать:** если покупатели ищут слово, которого нет в словаре, добавьте его в `SYNONYM_GROUPS` (для товаров) или в `keywords` нужного раздела `SITE_PAGES`. Каждое добавление проверяется в `tests/unit/search.test.ts`.

### Как устроено хранение товаров и как перейти на БД

- `server/repositories/product.repository.ts` — интерфейс `ProductRepository` (`listProducts`, `getProductBySlug`, `getProductsByIds`, `listCategories`, `getTaxonomy`) и фабрика `getProductRepository()`.
- Сейчас фабрика возвращает `json-product.repository.ts`: читает `data/` через Nitro server assets (попадают в сборку), валидирует zod-схемами, битые файлы пропускает с понятным логом, кэширует в памяти (в dev перечитывает на каждый запрос).
- Логика фильтрации, поиска, сортировки, фасетов и пагинации **не зависит от хранилища**: она работает с массивом товаров (`shared/utils/catalog-query.ts`).
- Переход на SQLite/MongoDB: напишите `sqlite-product.repository.ts`, реализующий тот же интерфейс, верните его из `getProductRepository()`. API-обработчики, страницы и компоненты менять не нужно. Для очень больших каталогов фильтры можно перенести в запросы БД, оставив ту же форму ответа `CatalogResult`.
- Админ-панель в этот этап не входила. Прежде чем редактировать товары через интерфейс, нужно отдельно спроектировать авторизацию и постоянное хранилище; запись в JSON-файлы как в базу не используется.

### Страница товара

- Характеристики показываются только известные; неизвестное названо неизвестным («Состав пока не указан») и предлагает спросить Дани (`ProductSpecs`, `ProductCare`).
- Пояснения рядом с характеристикой (`Explainer`, нативный `<details>`): общие сведения о материалах берутся из `data/materials.json`, а не пишутся в карточках; в них нет обещаний про тепло, колючесть и катышки.
- Размер: `SizePicker` (если размеров больше одного), справка `SizeDialog` с таблицей измерений, моделью и инструкцией. Выбор не сбрасывается при открытии справки или сообщения; размер попадает в корзину и в текст заказа. Остаток общий на изделие, а не на размер.
- Вопрос про изделие (`MessageDialog`): готовое сообщение с названием, размером и ссылкой; его видно целиком, копирует и открывает Telegram сам покупатель. Ничего не отправляется автоматически.
- Информационные страницы `/info/materials` и `/info/sizes` открываются с карточки с `?from=<slug>` и возвращают к изделию.

### Корзина и Telegram

- Корзина — Pinia + `localStorage` (ключ `sparkle-dani:cart:v1`), читается после гидратации; битые данные отбрасываются. Синхронизация между вкладками. На странице корзины цены и остатки подтягиваются из каталога (`/api/catalog.json`), исчезнувшие товары помечаются и не входят в сумму.
- Лимиты: для «в наличии» с заданным `stock` — не больше остатка; если остатка в данных нет — только технический потолок 99 шт. Ограничений не выдумываем.
- Кнопка «Связаться с Дани» открывает диалог с составом заказа и суммой. Текст **ничего не отправляет автоматически**: покупатель копирует его и сам открывает Telegram (`https://t.me/<TELEGRAM_USERNAME>`). Так состав заказа не уходит третьим лицам.
- Сейчас в `TELEGRAM_USERNAME` временно стоит `sosukii` — **замените на контакт Дани** в `shared/utils/site.ts`.

### Шрифты

Inter (интерфейс), Playfair Display (крупные русские заголовки) и Bodoni Moda (только латинский логотип: кириллицы в ней нет) лежат в `@fontsource-variable/*`. `scripts/build-fonts.mjs` перед сборкой делает из них облегчённые файлы: кириллица как есть, латиница урезана до нужных символов, разбивка по `unicode-range`. Критичные начертания предзагружаются, `font-display: swap`. Значка ₽ нет ни в одном из шрифтов (кроме системных), его рисует системный.

### Изображения

`scripts/optimize-images.mjs` перед dev/build/generate превращает исходники из `public/images/` в варианты 360/640/960/1200 px в AVIF, WebP и JPEG (`public/_img/`, в git не хранится; готовые файлы пропускаются). Компонент `AppImage` строит `<picture>` с явным `srcset`, `width/height` против сдвигов вёрстки и `sizes` под сетку; главная картинка первого экрана — `priority` (без lazy, `fetchpriority=high`, `preload`), остальные — `loading=lazy`. Так картинки работают на статическом хостинге без сервера обработки.

### SEO

Уникальные `title`/`description`, canonical, Open Graph (`usePageSeo`), `sitemap.xml` (страницы, категории, товары) и `robots.txt` (`/cart` закрыт) через `@nuxtjs/sitemap` и `@nuxtjs/robots`; фильтры, поиск и корзина — `noindex`; нормальные 404 со статусом 404; JSON-LD `WebSite` на главной и `Product` — только для не-демо товаров.

Уже сделано: картинки-заглушки облегчены вдвое, предзагрузка сокращена до четырёх критичных шрифтов (LCP 4.9 → 4.4 с). **Что дал аудит (история).** Первый замер (Node-сервер без сжатия) показал мобильный Perf 62–83 и CLS до 0.19. Шаги: сжатие; предзагрузка критичных шрифтов и облегчение шрифтов (−48 КБ, убраны лишние запросы «latin-ext»); фиксированная пропорция коллажа; данные страницы встроены в HTML (без отдельного `_payload.json`); CSS встроен в HTML статической сборки; резерв места под результаты поиска (CLS 0.3 → 0); исправлены контраст и порядок заголовков.
**Что не сработало и не вошло:** отказ от предзагрузки латинских шрифтов (стало хуже).
**Узкие места, которые остались:** на телефоне под жёстким троттлингом главная даёт LCP 3.3 с (шрифты + ~80 КБ gzip JS ядра Vue/Nuxt, которые не получится заметно срезать); на статике каталог дополнительно загружает `catalog.json` (≈25 КБ в gzip) при первом применении фильтра.

## Принятые решения

- **Nuxt 4, а не 3.** В ТЗ указан Nuxt 3, но на октябрь 2026 актуален Nuxt 4 (это тот же Vue/Nitro с обновлённой структурой `app/`), ветка 3.x устаревает. Вся архитектура прежняя.
- **Свой пайплайн картинок вместо `@nuxt/image`.** Разбор `sizes` в модуле давал мусорные варианты (`1×1`, `2×2`), а ресайз «на лету» нельзя запустить на GitHub Pages. Теперь размеры готовятся при сборке, `AppImage` строит `srcset` сам.
- **Данные одним JSON и фильтры в браузере.** Нужны, чтобы сайт жил на статическом хостинге; при росте каталога до тысяч позиций фильтры можно вернуть на сервер, оставив форму ответа `CatalogResult`.
- **Корзина читается через `onNuxtReady`, а не `app:mounted`.** `app:mounted` срабатывает до окончания гидратации страниц с асинхронными данными, из-за чего разметка расходилась с серверной.
- **Сжатие HTML — серверным плагином.** Не нужен отдельный прокси, но Nuxt собирает страницу ошибки внутренним подзапросом, поэтому он исключён (иначе бинарное тело ломалось). JSON из `/api/*` лучше сжимать на уровне прокси/CDN.
- **Теплота / сезон.** В ТЗ поле названо «Теплота / сезон» без деталей; сделан справочник «Тёплое / Демисезон / Лёгкое» (необязательное поле). Меняется в `data/taxonomy.json`.
- **Кнопка «Связаться с Дани».** В ТЗ имя «Даня», по решению заказчика на сайте — «Дани» (одно и то же лицо). Имя вынесено в константу `OWNER_NAME`.
- **Google Stitch не использовался:** в этом окружении он не подключён, дизайн сделан вручную.

## Известные ограничения и что дальше

- Демо-контент (товары, иллюстрации) нужно заменить настоящим; контакт Telegram — на контакт Дани; тексты «Обо мне» и «Покупка и доставка» — на авторские.
- GitHub Pages размещает сайт в подпапке, поэтому `robots.txt` (он обязан лежать в корне домена) там создать нельзя; для поисковиков есть `<meta robots>` и `sitemap.xml`. Для GitHub Pages нужен публичный репозиторий (на бесплатном тарифе).
- Эталоны скриншотов для macOS и Linux хранятся отдельно; обновление Linux-эталонов пока ручное через артефакт CI (см. выше). Можно автоматизировать отдельным workflow или Docker-образом Playwright.
- E2E и скриншоты против production-сборки занимают около минуты на коммит; параллелизм ограничен двумя воркерами, потому что картинки кодируются на лету и нагружают процессор.
- Нет: онлайн-оплаты, админ-панели, отзывов/рейтингов, многоязычности — по ТЗ.
